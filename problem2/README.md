# Mini Code Agent

一个用 Python 手写的命令行 Code Agent：用户用自然语言描述任务，Agent 通过读文件、搜索、改文件和执行命令来完成。**Agent 循环、重试与容错、上下文压缩、取消与恢复都是自己实现的，没有使用任何 Agent 框架**；只用了模型厂商的官方 SDK（`openai`、`google-genai`）和通用库（`typer`、`rich`、`pydantic`、`pydantic-settings`、`httpx`）。

接入两种协议不同的模型：

- **Qwen**（阿里云 DashScope 的 OpenAI Chat Completions 兼容接口）
- **Gemini**（Google 原生 `generate_content` 接口）

## 1. 安装与运行

### 环境

- Python 3.11 及以上（开发和测试用 3.12，**3.11 没有实测**；下限是 3.11 因为 `google-genai` 要求）
- [uv](https://docs.astral.sh/uv/)
- 已验证平台：**Windows 和 Linux（WSL Ubuntu）**，两者都用 Python 3.12 跑过完整测试；**macOS 未测试**

### 安装

```bash
cd problem2
uv sync
```

### 配置

复制 `.env.example` 为 `.env`（放在**运行命令的当前目录**）并填写，或直接设置环境变量。`.env` 已被 `.gitignore` 忽略，不要提交。

| 变量 | 说明 |
| --- | --- |
| `DASHSCOPE_API_KEY` | Qwen 的 Key |
| `QWEN_BASE_URL` | 默认 `https://dashscope.aliyuncs.com/compatible-mode/v1`，国际站等请自行改 |
| `QWEN_MODEL` | 默认 `qwen-plus` |
| `GEMINI_API_KEY` | Gemini 的 Key |
| `GEMINI_MODEL` | **没有默认值**，必须通过它或 `--model` 指定（我不猜模型名） |
| `MINI_AGENT_PROVIDER` | 默认提供者，`qwen` 或 `gemini`，默认 `qwen` |
| `MINI_AGENT_CONTEXT_WINDOW` | 模型的上下文窗口（token），默认 128000；达到它的 80% 时压缩历史 |
| `MINI_AGENT_HOME` | 会话和日志的存放目录，默认 `~/.mini-agent/` |

空值视为未设置。Key 在程序内部是 `SecretStr`，不会出现在 `repr`、日志或界面里。

### 运行

```bash
uv run mini-agent --workdir /path/to/project --provider qwen
uv run mini-agent --workdir /path/to/project --provider gemini --model <模型名>
```

Windows PowerShell 里路径写成 `D:\agent-sandbox` 即可。

| 参数 | 说明 |
| --- | --- |
| `--workdir` | Agent 只能访问的工作目录，默认当前目录 |
| `--provider` / `--model` | 选择提供者和模型 |
| `--yes` | 跳过 `write_file`、`edit_file`、`run_shell` 的 y/n 确认 |
| `--resume <会话 id>` | 恢复之前的会话并继续 |
| `--max-steps` | 单个任务的最大模型调用次数，默认 30 |
| `--context-window` | 覆盖上下文窗口大小（最小 2000） |
| `--log-file` | 日志位置，默认 `<状态目录>/logs/<会话 id>.log` |

交互里：直接输入任务；`/help` 显示帮助，`/exit` 退出（空闲时 Ctrl+D 或 Ctrl+C 也退出）。启动时会打印会话 id，退出时会提示 `mini-agent --resume <id>`。会话保存在 `<状态目录>/sessions/<id>.jsonl`，**不在工作目录里**，所以工具碰不到它。

## 3. 架构说明

### 模块划分

```
src/mini_agent/
├─ messages.py        内部消息格式（Pydantic）
├─ history.py         历史不变量：validate / repair / normalize
├─ config.py          AgentConfig、Settings（环境变量与 .env）
├─ cli.py  repl.py  ui.py   命令行、交互循环、终端渲染
├─ session.py         JSONL 会话持久化与恢复
├─ logging_.py        请求/响应日志与脱敏
├─ tokens.py          离线 token 估算
├─ agent/
│  ├─ loop.py         Agent 循环
│  ├─ compaction.py   上下文压缩（4.1）
│  ├─ cancel.py  interrupt.py   取消令牌与 Ctrl+C 策略（4.2）
│  ├─ text_toolcall.py  loop_detector.py   异常输出与死循环（4.3）
│  └─ prompt.py       系统提示词
├─ providers/
│  ├─ base.py         Provider 抽象：请求、流式事件、collect()
│  ├─ errors.py  retry.py   错误分类与指数退避重试
│  ├─ qwen.py  gemini.py  mock.py  factory.py
└─ tools/
   ├─ base.py  registry.py  sandbox.py  truncate.py
   └─ fs.py  shell.py     list_files read_file write_file edit_file grep / run_shell
```

### 内部消息格式

Agent 代码只接触一种与厂商无关的格式，厂商格式只在 Provider 边界转换。

- `Message(role, content)`，`role` 是 `user` 或 `assistant`；内容是块的列表：`TextBlock`、`ToolUseBlock`（id、name、input）、`ToolResultBlock`（tool_use_id、content、is_error）。
- **工具结果放在 user 消息里**（`tool_use` 在 assistant 消息，对应的 `tool_result` 在紧随其后的 user 消息）。这是各家协议里最严格的形式，其他形式都可以从它转换出来。
- `ToolUseBlock.meta` 保存厂商私有数据，必须原样回传（例如 Gemini 的 thought signature）；`raw_arguments` 保存无法解析成对象的参数原文，**非法 JSON 绝不存进 `input`**。

### 历史不变量

`history.py` 定义并检查五条不变量，所有 Provider 都要求它们成立：

1. 每个 `tool_use` 在下一条 user 消息里恰有一个对应结果
2. 没有孤立的 `tool_result`
3. 角色交替，且以 user 开头
4. `tool_use` 的 id 唯一
5. 没有空消息

`validate` 只检查；`repair` 修复，并且对合法历史是恒等的；`normalize` 只合并相邻同角色消息。Agent 循环靠**构造**保证历史合法，`validate`/`repair` 只是兜底；兜底一旦被用到会写进日志。

### Provider 抽象

三层，Agent 循环只依赖它们：

1. **请求** `ProviderRequest`：system、messages、tools、max_tokens
2. **流式事件** `StreamEvent`：`TextDelta`、`ToolCallStart`/`ToolCallArgsDelta`/`ToolCallEnd`、`UsageEvent`、`Done(stop_reason)`；分片的工具调用参数由 `StreamAccumulator` 按 id 拼接
3. **错误**：`RetryableError`（429、5xx、网络超时与断连，可带 `Retry-After`）、`FatalError`（401、400 等，直接报清晰的错）、`ContextLengthExceeded`（交给压缩处理）

Provider 实现自己把 SDK 异常映射成这三类。重试在 `providers/retry.py` 里自己实现：**关闭 SDK 自带的重试**，指数退避加抖动，默认最多重试 4 次、基础 1 秒、上限 30 秒，尊重 `Retry-After`；流式响应中途断开时丢弃这次的部分结果后整体重试。重试等待可被取消打断。

两个实现的主要差异（都在 Provider 内部消化）：

| | Qwen（OpenAI 协议） | Gemini（原生协议） |
| --- | --- | --- |
| 工具结果 | 多条 `role: tool` 消息，按 id 匹配 | `function_response`，**按函数名**匹配 |
| 调用 id | 服务端给 | 没有稳定 id，自己生成并标记，**不发送**生成的 id |
| 参数 | 流式分片，按 index 拼接 | 整个到达 |
| 特殊数据 | 忽略 `reasoning_content` | Gemini 3 要求回传 thought signature，存 `meta`（base64）并原样回传 |
| 429 | 按文字区分限流与额度耗尽 | 按 `QuotaFailure` 的 `quotaId` 区分，日配额耗尽不重试 |

### Agent 循环（`agent/loop.py`）

一个 step：校验历史 → 必要时压缩 → 带重试地流式调用 Provider → 提交 assistant 消息 → **按顺序**执行每个工具调用 → 把全部结果合成**一条** user 消息提交 → 继续，直到模型不再调用工具。

- 每个工具调用都必有结果：参数非法或被截断、未知工具、校验失败、用户拒绝、被中断，都会合成结果。
- 终止情形：回复完成；步数上限（默认 30）；**连续 5 次工具失败**（题目提到的"另一种情形"，我的理解；用户拒绝不计入，成功会重置计数）；死循环检测到最高级；取消；出错。达到上限时提交一条 assistant 说明，使历史以 assistant 结尾，用户说 "continue" 即可继续。
- 用户拒绝一次操作：把"用户拒绝，未执行"作为工具结果回填，会话继续。
- 多轮对话：同一会话的历史一直保留。
- 循环只依赖 `Provider`、`ToolRegistry`、`AgentUI` 三个接口，所以能用 Mock Provider 和记录型 UI 完整测试。

### 工具与安全边界

| 工具 | 说明 |
| --- | --- |
| `list_files` | 列目录或按 glob 匹配；忽略 `.git`、`node_modules` 等；最多 200 条 |
| `read_file` | 带行号，可按行范围读；每次最多 500 行 / 20000 字符，单行最多 2000 字符；二进制文件拒绝 |
| `write_file` | 创建或覆盖，自动创建父目录；确认时显示 diff |
| `edit_file` | `old_string` → `new_string`，必须**恰好匹配一次**（重叠匹配算多次），0 次或多次都返回说明原因的错误；CRLF、BOM 原样保留，非 UTF-8 文件拒绝并说明 |
| `grep` | 工作目录内按正则搜索，最多 100 条；跳过大于 20MB 的文件和二进制文件；不跟随指向目录外的链接 |
| `run_shell` | 默认超时 60 秒（最大 600）；返回 exit code、stdout、stderr；stdin 置空；超时或取消时杀整个进程树 |

每个工具是一个 Pydantic 参数模型加描述和 `run()`，JSON Schema 由 Pydantic 生成后清理。工具异常只会变成错误结果，不会让程序崩溃。

- **工作目录沙箱**：所有文件工具的路径都经过 `Sandbox` 解析，`../`、绝对路径、符号链接和 Windows 目录联接都不能逃出工作目录。
- **危险操作确认**：`write_file`/`edit_file` 显示 diff，`run_shell` 显示命令，`y/N`，只有明确的 y/yes 才通过；`--yes` 跳过；无法交互且没有 `--yes` 时视为拒绝。`edit_file` 的预览阶段就会报错，所以无效调用不会先让用户确认。
- `run_shell` 的非零退出码只是信息，不算工具失败；只有超时或取消才标记为错误，避免"连续失败终止"误伤"测试失败后再修"。
- 子进程的环境变量中，名字以 `API_KEY` 结尾的会被剔除。

### 日志与会话

- 日志（JSONL）完整记录会话开始、每次请求的完整消息、响应、重试、工具调用、压缩/循环检测事件和错误，**不记录请求头**，并对序列化后的整行脱敏（已知 Key 值，以及 `sk-`、`AIza`、`Bearer` 三类格式）。
- 会话（`session.py`）：JSONL，第一行是元信息，之后一条消息一行，每次追加都 `fsync`；`Agent.on_commit` 把每条提交的消息写盘。恢复见 4.2。

## 4. 第 4 章必做题：设计、取舍与局限

### 4.1 上下文溢出，以及压缩后消息序列的合法性

**场景**：让 Agent 分析 5MB 日志，或一个会话里连续做很多任务，历史超过模型的上下文窗口。

**设计（三层）**

1. **单个工具输出有硬上限**，超出部分截断并告诉模型怎么继续：`read_file` 截断时写明"文件共 N 行，已显示第 a–b 行，用 `start_line=…` 继续"；`run_shell` 只保留输出的头 4000 字节和尾 8000 字节并写明省略了多少；注册表对任何结果再兜底 30000 字符。
2. **每次请求前估算 token**，达到窗口的 80% 就压缩到约 50%。估算是离线启发式（ASCII 约 4 字符一个 token，非 ASCII 约 1.5 个 token 一字），再乘一个用供应商返回的真实 `input_tokens` 校准出的系数（比值不在 0.33–4 之间的数字不采信）。压缩分两层，先便宜的：
   - 第 1 层：把旧的、超过 200 字符的工具结果换成"已省略 N 行 M 字符，需要请重新运行工具"，把超过 400 字符的工具参数字符串换成 `<omitted N characters>`；块的类型、id、顺序和 `is_error` 都不动。
   - 第 2 层：把最旧的若干**单元**换成**一条**摘要 user 消息，后面保留原文的最近单元。
3. **估算偏低而供应商仍返回"上下文超长"**：强制压缩一次并重试一次，第二次仍超长就如实报错。

**如何保证压缩后仍然合法（题目的重点）**

先把历史切成**原子单元**：

```
[user 文本]                                        一个单元
[assistant 文本]                                   一个单元
[assistant（含 tool_use）+ 紧随的 user（全部 tool_result）]   一个单元
```

**切点只会落在单元之间**，所以"边界刚好落在一组工具调用中间"这种情况在结构上不可能出现；一条 assistant 消息有 3 个工具调用时，它和那条含 3 个结果的 user 消息永远在一起，要么都保留要么都进摘要。压缩产物是 `[摘要] + 保留的后缀`，摘要后面若紧跟 user 消息就合并以保持角色交替。最后无条件 `validate`；不合法就 `repair`，`repair` 一旦被用到会记入结果的 `notes`；仍不合法就放弃压缩、保留原历史并提示。

**关键信息保留**：摘要由三部分组成，前两部分**由代码维护，不依赖模型是否记得写**：

- 用户的全部原始请求（每条压成一行，最多 600 字符，最多 40 条）
- 已成功修改的文件列表（取自成功的 `write_file`/`edit_file` 调用；失败的编辑不算）
- 进度与未完成事项：向模型单独发一次摘要请求（无工具、`max_tokens` 1024，对话记录当作数据而不是指令）；失败或不可用时用规则兜底（最近 12 个动作加一句"未完成事项没有自动记录，请把最近一次请求当作可能未完成"）

前两部分能从旧摘要里解析回来，所以连续压缩多次、会话恢复后再压缩都不会丢。Agent 自己插入的纠正提示（以 `[Agent notice]` 开头）不会被当成用户请求。

**取舍**

- 不用 tiktoken：它首次使用要联网下载词表（评审环境可能没有网络），对 Qwen 和 Gemini 也不准。用启发式加真实用量校准，偏差由第 3 层兜住。
- 摘要多一次模型调用（成本），换来更好的"未完成事项"，失败时无损降级。
- **压缩不写入会话文件**：会话文件永远是完整记录，不会出现"压缩后的历史写坏"；代价是恢复后第一次请求可能多一次摘要调用。
- 压缩后 4 条消息内不再触发，防止每一步都压一次。

**局限**

- 估算是启发式，对代码和非英文内容可能偏差较大。
- 窗口大小靠配置（默认 128000）；Qwen、Gemini 的实际窗口不同时请用 `--context-window` 或 `MINI_AGENT_CONTEXT_WINDOW` 设置。
- 模型写的摘要可能遗漏细节，所以最关键的两部分不走模型；第 1 层把旧输出换成占位后，模型要重新运行工具才能再看到内容。
- 最新的一个单元永远原样保留。一条回复里的多个工具调用只构成**一个**单元：真实 Qwen 会把多个 `read_file` 放进同一条回复并行发出，它们和结果合成一个不可再分的单元。单个结果有 30000 字符的上限，但一条回复里的调用数量没有上限，所以一次并行读很多大文件时，这个最新单元可能本身就超过窗口，此时压缩无能为力，只能报错（默认 128000 的窗口下需要很多大文件才会出现）。
- 日志每步记录完整请求，不受压缩影响，体积随会话长度近似平方增长。
- **压缩在真实 Qwen 上验证过一次**（`--context-window 6000`，5 个回合各完整读一个文件，再问最初的请求）：从第 2 个回合起每个回合都触发了压缩（约 5445→3769、5730→3857、5862→3889、5917→3925 token，都是第 2 层摘要，用的是 Qwen 写的摘要），任务全程没有报错；压缩之后问"我最开始的请求是什么、读过哪些文件"，模型按顺序答对了。摘要的整体质量没有系统评估，只看到了这一次的输出；压缩后的大小（约 3800–3900）高于目标 3000，因为系统提示词和工具定义占了一部分，且最新的单元永远保留。这次真实运行还偶然验证了重试：压缩后的一次请求超时和断连，各重试一次后成功。

**测试**（`tests/test_compaction.py`，33 个）：一条 assistant 含 3 个 `tool_use` 加一条含 3 个 `tool_result` 的历史；**对预算逐一扫描**（含 1 个和 3 个调用的组、保留 1/2/3 个单元），每个结果都合法、没有走到 `repair()`、没有被编造的工具结果；负对照（按条数硬切会产生非法历史）；**变异检查**（在测试里用 `monkeypatch` 把 `split_units` 换成"每条消息一个单元"，扫描必须报问题）；两次连续压缩后原始请求和已改文件仍在；摘要失败时规则兜底；摘要期间取消历史不变；摘要文字不会作为回复显示给用户（这是真实运行暴露的 bug 的回归测试）；`ContextLengthExceeded` 强制压缩重试一次；5MB 日志经真实 `read_file`/`run_shell` 进入历史时有界。

### 4.2 中断、取消与会话恢复

**场景**：模型正在流式输出，或 `run_shell` 在跑一个很慢的命令，用户按 Ctrl+C。

**Ctrl+C 策略**：空闲的提示符下 Ctrl+C 退出程序；任务进行中**第一次只取消这一轮**，回到提示符，会话继续；2 秒内第二次才退出；在 y/n 确认提示处按 Ctrl+C 视为不同意并取消。实现为信号处理器：它**只设置取消令牌**，该抛异常才抛，不打印。取舍：不依赖 `KeyboardInterrupt`，因为它可能落在任何位置（包括修改历史的中途）；用令牌后，所有等待的代码在自己的安全点检查，历史由"只追加加对账"保证合法。

**取消如何传播**：`CancelToken`（线程安全、可在信号处理器里调用）贯穿三处：流式读取（`collect()` 在生产者线程里读 Provider 的流，调用方线程每 50 毫秒检查令牌，所以**网络静默阻塞也不影响取消**）、重试退避等待（0.1 秒切片，因为 Windows 上一次长时间的阻塞等待在结束前不会响应 Ctrl+C）、`run_shell`（0.1 秒轮询）。取消造成的连接错误会被报告为取消而不是网络错误。

**进程树终止**：`run_shell` 被取消或超时时杀整个进程树，不留孤儿：POSIX 用 `killpg`（先 SIGTERM，1 秒后 SIGKILL），Windows 用 `taskkill /F /T`。用"孙进程是否真的被杀死"的真实进程测试在 Windows 和 Linux 上验证。**支持平台：Windows 和 Linux；macOS 走 POSIX 路径但未测试。**

**取消后的历史（题目的重点问题）**

- 模型发出 3 个工具调用，只执行完 1 个就被取消：已完成的保留结果，执行中的补"被用户中断"，没执行的补 "NOT executed"。**每个调用都有结果**，作为一条 user 消息提交，所以下一次请求不会因为配对问题报 400。
- 流式输出到一半的 assistant 消息：**保留已经显示给用户的文本，丢弃不完整的 `tool_use`**（它的参数 JSON 不完整，也从没执行过，丢掉与屏幕上看到的一致），再追加一条 assistant 说明（"用户在此打断了回复"/"用户取消了任务"）。这样历史以 assistant 结尾，下一条 user 消息自然交替，模型也知道发生了什么。
- 取消前什么都没输出：只留一条说明，不留以 user 结尾的悬空消息。

**会话持久化与崩溃恢复**：每条消息提交就追加一行并 `fsync`，**先写后做**——`tool_use` 在工具执行前就落盘。所以崩溃发生在工具执行途中时，文件里会有"调用了但没结果"。`--resume <id>` 时：丢弃末尾不完整的半行；对每个没有结果的调用补一条"程序在执行途中退出，副作用未知，请先检查再重试"；任何改动都**原子重写**文件，免得下一次追加粘在残片后面；中间某行损坏则拒绝恢复并说明。`--resume` 沿用保存的工作目录，给了不同的 `--workdir` 就拒绝。会话 id 有格式限制，防止路径穿越。取舍：用 JSONL 逐条追加而不是每轮覆盖整份快照，因为崩溃最多损坏最后半行；代价是要处理半行和重写。

**局限**

- 被取消的 `run_shell` 已经产生的副作用（比如写了一半的文件）不会回滚，只会在结果里标明"被用户中断"。
- 用 `setsid`/`start` 主动脱离进程树的孙进程杀不到；后台进程仍握着输出管道时（`sleep 30 &`），`run_shell` 在 2 秒后返回已读到的输出，后台进程**不会被杀死**。
- 取消时被丢弃的流**不会被立刻关闭**，而是在它下一次收到数据、读超时（默认 120 秒）或结束时关闭；在此之前服务端可能还在生成（并计费）。程序本身不受影响（取消立刻生效）。我尝试让 Qwen 在取消时立即关闭 HTTP 响应，没有成功；Gemini 的 SDK 没有暴露可以从别的线程关闭的底层连接。
- 恢复只保证**历史合法**，不保证工作目录的文件状态没变。
- 同一个会话被两个进程同时打开没有加锁，行为未定义；会话文件和日志明文保存对话内容和工具输出，没有加密也没有自动清理。
- **真实按键的验证范围**：Linux 上用自动化测试给子进程发真实 `SIGINT`（单次 Ctrl+C 取消任务并杀死孙进程、程序继续运行并完成第二个任务）；Windows 上由我手动验证过一次——在请求失败后的重试等待中按 Ctrl+C，程序打印 `Cancelled.` 并回到提示符。**没有验证的**：在 `run_shell` 跑慢命令时的真实按键、2 秒内连按两次退出，以及确认提示处的 Ctrl+C；这几种只有自动化测试覆盖。

**测试**：`tests/test_cancel.py`（22 个，含 2 个仅 POSIX 的真实 SIGINT 用例）、`tests/test_session.py`（含端到端崩溃恢复）、`tests/test_cli_session.py`、`tests/test_shell.py`（进程树）、`tests/test_agent_loop.py::test_interrupted_tool_round_still_leaves_a_valid_history`。

### 4.3 模型异常输出的容错与死循环检测

使用 Pydantic：工具参数校验、文本工具调用的识别都是 Pydantic 模型。

**① 参数不是合法 JSON / 被 `max_tokens` 截断**（`finish_reason=length`、`stop_reason=max_tokens`）：**绝不修补后执行**。非法 JSON 不存进 `input`（原文放 `raw_arguments`）；这样的调用不会执行，回填一条错误，指出参数被截断、建议缩小单次内容（例如先 `write_file` 写短的，再用多次 `edit_file` 扩展）。

**② 调用了不存在的工具，或参数缺必填字段、类型不对**：Pydantic 的 `ValidationError` 整理成简明提示（缺少哪个字段、哪个字段类型不对、给了什么值、有哪些合法字段）；未知工具附可用工具列表和 `difflib` 的近似建议。这些都是工具错误结果，任务继续。

**③ 把工具调用写进了普通文本**：我选择**识别，但不执行，提示模型改正**（题目允许二选一）。

- 识别方式：在回复文本里按 JSON 对象扫描（一次扫描同时覆盖裸 JSON、代码围栏和 `<tool_call>` 标签），用 Pydantic 模型校验，接受 `{"name","arguments"}`、`tool` 加 `parameters`、OpenAI 的 `{"function": {...}}`（参数是 JSON 字符串）等常见形状；只有**工具名是已注册的工具且带参数字段**才算，所以回答里普通的 JSON（`package.json`、接口示例）不会被误认。
- 处理：不执行，向历史追加一条 `[Agent notice]` 开头的 user 提示，要求改用工具调用接口；每个任务最多纠正 2 次，之后停下并告知用户。
- 为什么不执行：执行文本里的 JSON 会绕开原生通道的参数校验和截断检测，还会把"文件内容 → 模型复述 → 被执行"变成注入通道；提示改正实现最简单、风险最小。

**④ 死循环检测**：每次工具调用记成（签名，结果摘要），签名是工具名加规范化参数（键排序的 JSON，键顺序和空格无关）。

- 规则 A：同一调用且**结果相同**连续 3 次（例如连续读同一个文件、反复执行同一个失败的命令）。
- 规则 B：周期 2 到 3 的循环重复 3 轮（例如读 a → 跑测试 → 读 a → 跑测试 …）。
- **比对结果**是为了降低误报：改完代码后重跑同一条测试命令是正常进展，输出变了就不算重复。
- 升级：循环**持续**时每多一条记录升一级——第 1 级在该工具结果末尾追加提示，第 2 级追加更强硬的提示（说明再重复就会停止），第 3 级停止任务，由助手提交一条询问用户的消息；打破模式的任何一条记录都让级别归零。提示追加在工具结果里而不是新增消息，不影响角色交替和配对。阈值（3 次、周期 3）可配置。

**永不崩溃**：空响应重试 2 次后明确报错；`stop_reason` 为 `error`（例如内容过滤）的回复里的工具调用一律不执行并提示用户；Gemini 的 `MALFORMED_FUNCTION_CALL` 当作可重试错误；意外异常变成 `error` 状态，会话仍可继续。

**局限**

- 文本工具调用只认 JSON 形状；XML 风格（`<function=name><parameter=...>`）、Python 函数调用写法和未注册的工具名都不识别，会被当作普通回答。回答里恰好展示"已注册工具名加参数"的 JSON 示例时会被误认，代价是多一次纠正。
- 死循环检测不理解语义：**会误报**轮询类命令（例如反复 `curl` 等服务起来而结果恰好不变）和故意重复读同一个文件；**会漏报**每次参数略有不同（例如每次读不同行号）的无进展循环，以及周期超过 3 的循环。
- **真实模型验证（Qwen，各只做了一次，都是我刻意诱导出来的，不是模型自然出错）**：
  - 死循环：我要求它连续读 `a.txt` 六次。前两次正常，第 3、4 次的工具结果后面带上了循环提示（终端里该结果显示为"+1 more lines"），模型随后自己停下并说明运行环境的循环保护阻止了它继续重复。所以第 1、2 级提示在真实模型上起了作用；**第 3 级（强制停止）没有在真实运行里走到**，只在 Mock 上验证过。我没有核对日志里的 `loop_detected` 事件，证据是终端输出和模型的回复。
  - 文本工具调用：我要求它不要用工具调用、把一段 `{"name": "read_file", "arguments": {...}}` 原样写进正文。界面出现了纠正提示，文本里的调用没有被执行（屏幕上没有 `read_file` 的执行行），模型随后说明那只是格式测试并给出文字回答。这是被用户明确要求而写成文本的，不是模型自己写错；它也说明这种情形下会多花一次模型调用。
- 其余（内容过滤分支、阈值是否合适、真实模型自己写成文本的概率）没有观察，阈值没有在真实模型上调过。

**测试**（`tests/test_robustness.py`，46 个；截断参数、空响应、校验报错的单元测试在 `tests/test_agent_loop.py` 和 `tests/test_tools.py`）：未知工具/缺字段/类型错误在 Agent 里端到端且纠正后任务继续；文本工具调用 6 种写法被识别、9 种普通文本或数据不误认；文本调用不被执行（用会创建文件的调用证明文件没出现）；纠正用完后停下；检测器的各规则、升级、归零、阈值；Agent 端到端的提示、停止、一条回复里的多个相同调用中途停止且每个都有结果。另做了进程内变异检查：关闭循环检测、关闭文本识别、让检测器忽略结果、对被过滤的回复照常执行工具，这四种变异都会让测试失败。

## 5. 安全边界与已知局限

- **沙箱只约束文件工具**。`run_shell` 本质上无法被沙箱约束（命令里可以 `cd ..`、读绝对路径），只靠用户确认和环境变量清洗降低风险；确认提示只能显示"将要执行什么"，看不出副作用，最终依赖用户判断。
- 环境变量清洗只剔除名字以 `API_KEY` 结尾的变量，其他命名的密钥不会被剔除。
- 日志脱敏只覆盖已知的 Key 值和 `sk-`/`AIza`/`Bearer` 三类格式；用户贴进对话的其他格式密钥不一定能被识别。日志默认含你的代码内容，不要随意分享。界面上显示的错误信息也脱敏，但模型输出的文本和工具结果摘要是原样显示。
- Prompt Injection：系统提示词要求把文件内容和命令输出当数据而不是指令，但这只是提示词层面的约束，**没有机制层面的防护，也没有测试**；真正的防线是危险操作需要用户确认。
- `list_files`/`grep` 用固定的忽略目录集合，不解析 `.gitignore`。
- 命令输出解码：先试 UTF-8，再回退到系统代码页；极端混合编码可能出现替换字符。
- `.env` 只从当前目录读取；REPL 只有 `/help` 和 `/exit`，没有 `/model`（中途切换模型是选做项，没有做）。`--resume` 换提供者时历史能用，但 Gemini 的 thought signature 只存在于 Gemini 产生的历史里，跨协议的完整支持没有专门处理。
- Qwen：只测过一个模型和国内站默认地址；错误处理依赖 `openai` 的异常类型和它内部用的 `httpx2`，SDK 大版本升级可能需要调整。
- Gemini：思考模型的推理 token 计入 `max_output_tokens`，默认 4096 在复杂任务上可能不够，全部额度被推理用完时会提示调大；不支持 Gemini 3 的"流式函数调用参数"功能；没有签名的手工构造历史会被服务端拒绝（已映射成清晰的错误）；国内网络访问可能需要代理。
- 我没有做过针对整个项目的变异测试；只在 4.1 的切点逻辑和 4.3 的四处关键逻辑上做过（见上）。

## 7. AI 使用说明

### 用了哪些工具，用在哪些部分

使用 GitHub Copilot CLI（对话式的编程 Agent），贯穿整个项目：先让它根据题目出详细的工作流文档（每个阶段、每个可选项和推荐、考察点），我选定方案后，由它按阶段实现问题二的代码和测试，并写了问题一的方案文档的初稿；每个阶段结束后更新进度文档。每个阶段的 commit 由我自己提交。

### AI 给的方案有问题的地方，以及怎么发现和修正的

下面都是开发中真实发生的：

1. **`read_file` 的续读提示被覆盖**（工具层）：AI 实现的 `read_file` 字符预算恰好等于注册表兜底的截断上限，结果自己的"用 `start_line=…` 继续读"提示被通用截断提示盖掉了。是"大文件截断后用行号继续读"的测试发现的，把预算降到 20000 修复。
2. **后台进程拖住 `run_shell`**（工具层）：AI 实现的读线程清理在 2 秒超时后对仍被阻塞的流调用 `close()`，而关闭一个正被别的线程读取的缓冲流会一直等到读返回，导致 `sleep 30 &` 让工具阻塞 30 秒。这在 Windows 上没有暴露，是我在 Linux（WSL）上跑测试时发现的；修复为"读线程共用 2 秒期限，只关闭已结束的读线程的流"，并新增一个跨平台回归用例。这个案例说明为什么要在两个平台都跑测试。
3. **对 SDK 的"推荐用法"没验证它实际发出什么**（Gemini）：AI 最初用 SDK 新推荐的 `parameters_json_schema` 字段直接传 JSON Schema。把测试写成"比较整个工具声明"后发现，SDK 实际发出的字段名和默认 API 版本无法离线确认服务端是否接受，于是改用所有 API 版本都支持的经典 `parameters`（自己写了约 20 行转换），并加测试保证 6 个真实工具转换后属性和必填字段都不丢。
4. **一条看起来很强的测试其实抓不住缺陷**（压缩）：我最初写的"对每个预算压缩后历史都合法"的扫描测试一直通过。用 `monkeypatch` 把 `split_units` 换成"每条消息一个单元"的错误版本后，它**仍然通过**——因为错误的切法留下孤立的结果，而 `repair()` 把它们删掉，历史重新合法，测试只检查"合法"所以看不出来。处理：让 `compact` 在走到 `repair()` 时记录下来，扫描同时检查"兜底没被用到"和"没有被编造的结果"，再加上这条变异用例。教训是兜底机制会掩盖上游缺陷，测试要断言兜底没被用到。
5. **Mock 测试漏掉、真实运行才暴露的 bug**（压缩）：压缩的摘要调用和正常回复走同一条流式路径，模型写的 `Goal / Done / Unfinished / Key facts` 被当成回复打印到了终端。我的 Mock 摘要用例只断言了请求内容和用量，**没有断言界面输出**，所以 32 个压缩测试全过也没发现；我用真实 Qwen 跑压缩时在屏幕上直接看到了。修复是让摘要调用不接文本回调，并补一条断言摘要文字不出现在界面、同时真实回复仍在的测试，再把修复撤销一次确认这条测试会失败。教训：Mock 只能证明你想到的断言；"内部调用不应对用户可见"这类行为要在界面一侧显式断言。修复后我没有再用真实 Qwen 复验。
6. **一条"取消立刻返回"的测试证明不了任何东西**（取消）：我最先写的用例用了会自己响应取消令牌的 Mock，所以就算没有生产者线程它也会通过。补了一条真正的用例：一个忽略令牌、永远不返回的流，旧实现会阻塞 30 秒、超过断言的 3 秒上限。
7. **真实信号测试里的错误假设**（取消）：AI 写的"连发两次 SIGINT 应该退出并提示 Quitting"在 Linux 上失败。原因是测试的假设错了：Python 会把连续到达的同种信号合并成一次，而且被取消的任务约 50 毫秒就结束了，第二次按键到达时程序已经空闲，按设计"空闲时 Ctrl+C 退出"不会出现 Quitting。改为用一个忽略 SIGTERM 的命令让取消变慢，并在两次信号之间隔 0.3 秒。
8. **测试隔离漏洞**（配置）：AI 写的 CLI 测试会读当前目录的 `.env`，如果开发者在项目目录里放了真实 Key，"缺少 Key"的测试就会读到它。复查隔离性时发现，加了自动夹具：清掉 Key 相关环境变量，并让每个测试在空的临时目录里运行。这一点只靠机制保证，我没有用真实 `.env` 实测过。
9. **弱断言**（Qwen）：AI 写的 `test_unexpected_exceptions_are_not_hidden` 用了一串 `or` 组合断言，几乎什么结果都能通过。复查时发现，先用一次性脚本确认 SDK 对意外异常的真实行为，再改成 `pytest.raises(..., match=...)` 的精确断言。
10. **依赖版本**（脚手架）：AI 最初把 `requires-python` 写成 `>=3.10`，`google-genai` 实际要求 3.11 及以上，`uv sync` 解析失败后改成 3.11。
